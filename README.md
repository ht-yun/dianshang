# 电商智能库存补货系统

> 打通「爬价比价 → 多平台库存同步 → AI 补货推荐 → 人工核验 → 供应商采购单 → 入库回写 → 可视化看板」的完整闭环。

一套可直接本地运行的全栈库存中台，解决多平台电商卖家最痛的三件事：**不知道补多少、补货来不及、各渠道库存对不上**。

## 一、快速开始

### 环境要求

| 项目 | 要求 |
| --- | --- |
| Node.js | **22.5.0 或更高**（依赖内置 `node:sqlite` 模块，无需编译原生依赖） |
| 操作系统 | Windows / macOS / Linux |
| 浏览器 | Chrome / Edge / Firefox 现代浏览器 |

> 检查版本：`node -v`

### 启动方式

**方式一：双击启动（Windows 推荐）**

双击项目根目录的 `启动系统.bat`，自动完成依赖安装、启动服务并打开浏览器。

若要同时运行**仿真数据子系统**（双系统联动），双击 `启动全部系统.bat`，
它会额外弹出一个数据源窗口（端口 4100）并启动主系统。

**方式二：命令行**

```bash
npm install      # 首次运行安装依赖
npm start        # 启动服务
```

看到以下提示即启动成功：

```
╔══════════════════════════════════════════════════╗
║   电商智能库存补货系统  v1.0.0                   ║
║   服务已启动 → http://127.0.0.1:3000             ║
╚══════════════════════════════════════════════════╝
```

浏览器访问 **http://localhost:3000** 即可使用。

首次启动会自动生成 18 个商品、4 个平台、5 家供应商、90 天销售历史的演示数据，
无需任何额外配置，打开即是一个在运转的真实业务系统。

## 三、双系统架构与数据源接入

系统由**两个独立进程**组成，职责严格分离：

```
┌─────────────────────────┐         ┌──────────────────────────────┐
│  仿真数据子系统 :4100    │         │  智能补货主系统 :3000         │
│  mock-data-service      │  HTTP   │                              │
│                         │ ──────▶ │  ┌────────────────────────┐  │
│  · 商品池（240 个）      │  JSON   │  │ 数据源适配层            │  │
│  · 时间推进模型          │         │  │ 字段映射 / 库存分摊      │  │
│  · 库存消耗与补货事件    │         │  │ 销量增量 / 快照记录      │  │
│  · 零依赖 · 可独立运行   │         │  └───────────┬────────────┘  │
└─────────────────────────┘         │              ▼               │
                                    │  商品 / 库存 / 销量 → 补货算法 │
                                    │  → 建议 → 采购单 → 可视化看板  │
                                    └──────────────────────────────┘
```

**为什么要拆成两个系统**

| 理由 | 说明 |
| --- | --- |
| 数据与业务解耦 | 数据生产方的字段契约是唯一耦合点，生产方可以随便换，业务方不用动 |
| 可替换性 | 将来对接真实电商 API，只改适配层的 `fetchProducts()`，补货算法与看板零改动 |
| 可独立演示 | 数据源可以单独启动、单独压测、单独重启，不影响主系统已有数据 |
| 职责清晰 | 一个只负责"造数据"，一个只负责"算补货"，符合真实企业系统的边界划分 |

### 启动两套服务

**一键启动（Windows）**：双击根目录 `启动全部系统.bat`，会弹出数据源窗口并启动主系统。

**手动启动**：

```bash
# 终端 1：数据生产方（零依赖，无需 npm install）
cd mock-data-service && npm start        # → http://127.0.0.1:4100

# 终端 2：业务消费方
npm start                                 # → http://localhost:3000
```

### 完成联动

主系统左侧菜单进入 **「数据源接入」**：

1. 确认地址为 `http://127.0.0.1:4100`，点 **测试连接** 可预览接口返回的原始数据；
2. 点 **立即同步**，仿真商品写入主系统（自动分摊到 4 个平台、回填 30 天销量历史）；
3. 打开 **定时同步** 开关，按设定间隔自动拉取；
4. 到「商品库存」「智能补货」页面，即可看到仿真商品参与补货计算。

> **重要**：启用定时同步后，主系统内置的订单模拟会自动停止。
> 库存只能有一个数据来源，两套来源同时改写会产生无法解释的跳变。

### 演示「新商品上架」

页面上的 **「新商品上架演示」** 卡片，用 `chaos` 模式模拟供应商不断上新：

1. 填上架数量（默认 5），点 **上架一批新商品**；
2. 弹窗列出本次新上架的 SKU、品类、价格与库存，并给出商品总数变化；
3. 关掉弹窗后，新商品立刻出现在「已接入的仿真商品」表格里，也已进入补货算法的计算范围；
4. 在表格里点任一商品的 **上游对照**，可并排比对「数据源原始值」与「主系统落库值」——库存、30 日销量、售价三行差异一目了然，用来证明映射没有失真。

> 上架演示只影响这一次请求，不会改动已保存的拉取模式。但如果把 `chaos` 设为默认模式并开启定时同步，商品数会持续增长——页面上对此有警示。

### 数据源接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/products?count=10&mode=stable` | 生成随机商品数据（核心接口） |
| GET | `/api/products/:item_id` | 单商品查询，附 30 日逐日销量（`fields` 可裁剪） |
| GET | `/api/products/stream` | SSE 持续推送 |
| GET | `/api/health` | 健康检查（含商品池状态分布） |
| GET | `/api/schema` | 字段契约 |
| GET | `/api/stats` | 生成器运行统计 |
| POST | `/api/reset` | 重置商品池 |

字段契约共 7 个必须字段：`item_id / title / stock / sales / price / category / min_stock`，
取值范围严格约束为库存 `0~500`、月销量 `0~3000`、价格 `10~300` 元。

三种拉取模式：

| 模式 | 行为 | 适用 |
| --- | --- | --- |
| `stable` | 固定切片，每次命中同一批商品，数值随时间演进 | **主系统默认**，可观察库存逐步下降 |
| `pool` | 从商品池随机抽取 | 通用演示 |
| `chaos` | 每次返回全新商品 | 模拟新商品不断上架 |

详细文档见 [`mock-data-service/README.md`](mock-data-service/README.md)。

### 数据为什么"像真的"

生成器内部跑了一个微型业务模型，而不是直接 `Math.random()` 取值：

- **时间推进**：每次请求推进 1~3 个仿真小时，按电商作息曲线（凌晨低、午间与晚间双高峰）消耗库存
- **日切滚动**：跨天后 30 日销量窗口滚动、趋势因子随机游走、价格按店铺习惯缓慢调价（`.9` 结尾）
- **补货事件**：库存低于阈值时有概率"供应商到货"，避免库存永久归零失去观察价值
- **场景覆盖**：库存按业务场景抽样（断货 8% / 紧缺 20% / 健康 52% / 积压 20%），
  保证预警、补货建议、积压提醒都有素材可演示
- **商品身份稳定**：按固定种子建池，服务重启后货号与标题不变，只有数值重新演进

## 五、技术架构

```
┌──────────────────────────────────────────────────┐
│  表现层  原生 ES Module + ECharts 5（本地离线）    │
│  8 个视图 · SSE 实时刷新 · 零构建步骤              │
├──────────────────────────────────────────────────┤
│  接口层  Express 4 · RESTful · 统一错误格式        │
├──────────────────────────────────────────────────┤
│  业务层  预测 · 补货算法 · 同步引擎 · 采集 · 预警  │
├──────────────────────────────────────────────────┤
│  数据层  SQLite（node:sqlite）· 12 张关系表        │
└──────────────────────────────────────────────────┘
```

**技术选型理由**

- **为什么用 `node:sqlite` 而不是 MySQL/PostgreSQL**：本地演示场景下零安装、零配置、单文件可拷贝，同时保留完整的关系模型（外键、事务、索引）。数据访问层已封装为 `db.js`，若需迁移到 MySQL 只需替换该层实现。
- **为什么前端不用构建工具**：答辩演示要求"打开就能跑、断网也能跑"。原生 ESM + 本地 ECharts 消除了 `npm build` 环节和网络依赖，避免现场演示翻车。
- **为什么用 SSE 而不是 WebSocket**：库存推送是典型的单向服务端消息流，SSE 基于 HTTP 无需额外协议升级，断线自动重连，实现成本和运维复杂度都更低。
- **为什么仿真数据源做成零依赖的独立进程**：数据生产方只需要 `node:http`，不装任何包、不碰数据库、不联网。这样它可以单独启动、单独重启、单独压测，也不会因为主系统升级依赖而被牵连；同时强制了"只通过 HTTP 契约耦合"的边界。

## 六、核心算法

系统刻意把每一步推导都做成「可解释」的——在补货建议页点「算法推演」，能看到从需求预测到补货量的完整计算过程，公式、代入值、中间结果全部展开。

### 1. 需求预测

```
Holt 双参数指数平滑：
  level_t  = α·y_t + (1-α)(level_{t-1} + trend_{t-1})
  trend_t  = β·(level_t - level_{t-1}) + (1-β)·trend_{t-1}

加权移动平均：WMA = 0.5·M7 + 0.3·M14 + 0.2·M30

融合预测：d̄ = 0.65·Holt + 0.35·WMA
```

Holt 捕捉趋势变化快，WMA 抗噪稳定，两者融合既能跟随销量爬升，又不会被单日促销脉冲带偏。最后再做合理性夹逼（不超过近 7 日均值的 1.8 倍），防止趋势外推失控。

### 2. 动态安全库存

```
SS = z · √(L·σd² + d̄²·σL²)
```

- `z`：服务水平对应的正态分位数（95% → 1.645，由 Acklam 近似算法求解）
- `L`：供应商补货提前期，`σL`：交期波动标准差
- `σd`：需求标准差

**关键点**：同时考虑「需求波动」和「供应商交期波动」。传统做法只算前者，一旦供应商交期不稳定就会频繁断货——这正是中小卖家最常见的隐性亏损来源。

### 3. 再订货点与补货量

```
ROP     = d̄·L + SS                        # 库存跌破此线立即补货
Target  = d̄·(L + 覆盖天数) + SS           # 补货后要达到的水位
Q       = Target − 可用库存 − 在途库存      # 在途抵扣，避免重复采购
Q_final = ceil(Q / MOQ) · MOQ             # 按最小起订量向上取整
```

### 4. 经济订货批量（参考值）

```
EOQ = √(2·D·S / H)
```
D 为年需求量，S 为单次订货固定成本（默认 200 元），H 为单件年持有成本（货值 20%）。

### 5. 库存健康度分档

| 状态 | 判定条件 | 系统动作 |
| --- | --- | --- |
| 已断货 | 可售 = 0 | 紧急预警 + 立即生成建议 |
| 低于安全库存 | 可售 < SS | 紧急预警 + 补货建议 |
| 达到补货线 | 可售 < ROP | 警告 + 补货建议 |
| 库存健康 | SS ≤ 可售 ≤ 积压线 | 不打扰 |
| 库存积压 | 可售天数 > 90 天 | 提示预警 + 建议暂缓采购 |

### 6. 自定义补货公式

设置页支持企业自定义补货规则，例如：

```
avg_daily * (lead_time + cover_days) + safety_stock - available - in_transit
```

公式由自研的递归下降解析器求值，**不使用 `eval` / `new Function`**，从根本上杜绝代码注入。
可用变量：`available` `in_transit` `avg_daily` `demand_std` `lead_time` `safety_stock`
`reorder_point` `cover_days` `moq` `eoq` `stock_days` `target_stock` `service_z`

公式写错时系统自动回落默认算法，业务不中断。

再演示「新商品上架演示」：填数量 → 上架 → 弹窗列出本次新上架的 SKU 与商品总数变化，说明这正是真实供应商上新的形态。

## 十、常见问题

**Q：启动报错 `Cannot find module 'node:sqlite'`**
Node.js 版本过低。需要 22.5.0+，执行 `node -v` 确认，升级后重试。

**Q：端口 3000 被占用**
```bash
PORT=3001 npm start        # macOS / Linux
set PORT=3001 && npm start # Windows CMD
```

**Q：想让同事在同一局域网访问**
```bash
HOST=0.0.0.0 npm start
```
然后其他设备访问 `http://你的电脑IP:3000`。注意 Windows 防火墙需放行 Node.js。

**Q：数据被改乱了想恢复初始状态**
```bash
npm run reset
```
（会清空所有采购单、预警、审核记录，重建演示数据）

**Q：真实抓取为什么总是回落模拟数据**
淘宝、京东等平台有严格反爬策略，服务端直连通常拿不到价格。系统已做优雅降级，模拟源同样能完整演示业务闭环。生产环境建议接入官方开放平台 API 或第三方价格监控服务。

**Q：主系统提示「数据源不可达」**
仿真数据源没启动或地址填错。先在浏览器打开 `http://127.0.0.1:4100/api/health`，
能返回 JSON 就说明服务正常；打不开则执行 `npm run mock` 或双击 `mock-data-service/启动仿真数据源.bat`。

**Q：仿真数据源端口 4100 被占用**
`MOCK_PORT=4101 npm start`（在 mock-data-service 目录下），然后到「数据源接入」把地址改成
`http://127.0.0.1:4101` 并保存。

**Q：接入仿真商品后，看板不再实时跳动了**
启用数据源定时同步后，内置订单模拟会停止（库存只能有一个来源）。这是预期行为；
关闭「定时同步」开关即可恢复内置模拟。

## 十一、安全与边界说明

- **无代码注入风险**：自定义公式走自研解析器，白名单变量与函数，`process.exit(1)` 这类输入会被直接拒绝。
- **SQL 全参数化**：所有查询使用预编译参数绑定，无字符串拼接。
- **XSS 防护**：前端所有动态文本经 `esc()` 转义后再插入 DOM。
- **参数边界校验**：算法参数有合法区间限制，异常输入返回明确错误提示而非静默失败。
- **本系统为演示/竞赛项目**：未实现用户登录与权限体系，请勿直接部署到公网生产环境。如需上线，需补充鉴权、HTTPS、操作审计与数据库备份策略。
