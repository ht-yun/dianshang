# 商品仿真数据生成子系统

电商商品业务数据的**数据生产者**。独立进程运行，通过 HTTP 对外输出随机生成的商品 JSON 数据，
供「智能库存补货系统」消费；也可以被任何其他系统当作数据源接入。

- 独立部署：不依赖主系统、不连数据库、不联网、**零第三方依赖**
- 每次请求结果都不同：内置业务时间模型，库存与销量持续演进
- 可替换：字段契约固定，将来换成真实电商 API 时上层业务无需改动

---

## 一、快速启动

### 方式一：双击启动（Windows）

双击本目录下的 **`启动仿真数据源.bat`**，窗口显示启动成功后即可访问。

### 方式二：命令行

```bash
cd mock-data-service
npm start
```

> 本项目没有任何第三方依赖，**不需要执行 `npm install`**，也不需要联网。

启动成功后会看到：

```
  ╔══════════════════════════════════════════════════════╗
  ║   商品仿真数据生成子系统  v1.0.0                     ║
  ╠══════════════════════════════════════════════════════╣
  ║   服务已启动 → http://127.0.0.1:4100                  ║
  ╚══════════════════════════════════════════════════════╝
```

### 立即验证

浏览器打开 **http://127.0.0.1:4100** 可看到可视化控制台；
或在命令行直接请求接口：

```bash
# Windows PowerShell
curl http://127.0.0.1:4100/api/products?count=5

# macOS / Linux
curl "http://127.0.0.1:4100/api/products?count=5"
```

连续执行两次，会看到返回的商品与数值都不一样 —— 这就是"源源不断产生数据"的效果。

## 二、接口清单

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 浏览器调试控制台（实时刷新表格） |
| GET | `/api/products` | **核心接口**：生成一批随机商品数据 |
| POST | `/api/products` | 同上，参数放 JSON body |
| GET | `/api/products/:item_id` | **单商品查询**：按编号回查一个商品，附 30 日逐日销量 |
| GET | `/api/products/stream` | SSE 持续推送，每 2 秒一批 |
| GET | `/api/health` | 健康检查（主系统用它探测连通性） |
| GET | `/api/schema` | 字段契约说明 |
| GET | `/api/categories` | 可用品类与价格带 |
| GET | `/api/stats` | 生成器运行统计 |
| POST | `/api/reset` | 重置商品池 |

所有接口均返回 `Access-Control-Allow-Origin: *`，可被任意来源的前端直接调用。

### 核心接口参数

`GET /api/products`

| 参数 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `count` | int | 随机 5~15 | 返回条数，上限 200 |
| `mode` | string | `pool` | 见下方「三种模式」 |
| `category` | string | 全部 | 按品类过滤，如 `数码配件` |
| `offset` | int | 0 | `stable` 模式的起始下标 |
| `seed` | string | 无 | 传入则本次结果可复现（用于排查问题） |
| `flat` | 0/1 | 0 | `1` 时直接返回数组，不带外层包装 |

### 三种模式

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `pool`（默认） | 从商品池**随机抽取**，商品身份稳定、数值随时间演进 | 通用演示 |
| `stable` | 按 `offset/count` 返回池中**固定切片** | 主系统反复同步同一批商品，观察库存逐步下降 |
| `chaos` | 每次返回**全新商品** | 模拟新商品不断上架、接口压测 |

> 主系统接入默认使用 `stable`：只有商品身份稳定，才能观察到「库存下降 → 触发补货」的完整过程。
> 若用 `pool`，每次同步都会抽到不同商品，主系统里的商品会越积越多。

### 单商品查询

`GET /api/products/MOCK-7K3F9A`

除了返回与列表接口一致的 7 个必须字段，还会额外给出内部模拟状态——这是「这个数是怎么来的」的凭证：

| 附加字段 | 说明 |
|---|---|
| `daily_sales` | 近 30 天逐日销量数组，可直接画走势图 |
| `avg_daily` | 日均销量（预测算法的输入） |
| `trend` | 趋势因子，>1 表示上升 |
| `promo_active` | 当前是否处于促销脉冲期 |
| `scenario` | 该商品的初始场景（`new`/`steady`/`hot`/`slow`） |
| `pooled` | 是否属于常驻商品池 |

支持 `?fields=stock,price` 裁剪返回字段，便于前端只取所需。

**查询是只读的**：不会推进全局仿真时钟，否则每查一次就会把库存「偷跑」一点，后续批量请求拿到的数据就不自洽了。因此连续查两次同一商品，值完全相同——要看到变化，请调用 `/api/products` 让时钟前进。

对于 `chaos` 模式生成的临时商品，本接口从一个容量 500 的**最近上架缓存**中回查（`pooled: false`），超出容量后按最早上架顺序淘汰，返回 404。这样既能让上游对照随时可用，又不会让内存无限增长。

## 三、字段契约

```json
{
  "item_id": "MOCK-7K3F9A",
  "title": "青禾 无线蓝牙耳机 主动降噪 超长续航 深空灰",
  "stock": 128,
  "sales": 1450,
  "price": 199.9,
  "category": "数码配件",
  "min_stock": 96,
  "stock_status": "low",
  "cover_days": 2.7,
  "updated_at": "2026-11-02T04:05:04.490Z"
}
```

| 字段 | 类型 | 取值范围 | 是否必须 | 说明 |
|---|---|---|---|---|
| `item_id` | string | `MOCK-XXXXXX` | ✅ | 商品唯一编号 |
| `title` | string | — | ✅ | 商品标题（品牌+商品+卖点+规格） |
| `stock` | int | **0 ~ 500** | ✅ | 当前可售库存 |
| `sales` | int | **0 ~ 3000** | ✅ | 近 30 天累计销量 |
| `price` | number | **10 ~ 300** | ✅ | 商品售价（元） |
| `category` | string | 8 个品类 | ✅ | 商品品类 |
| `min_stock` | int | 10 ~ 480 | ✅ | 补货阈值，库存低于此值应补货 |
| `stock_status` | string | `out`/`low`/`healthy`/`overstock` | 扩展 | 库存状态，便于直接展示 |
| `cover_days` | number | — | 扩展 | 库存可售天数 |
| `updated_at` | string | ISO8601 | 扩展 | 数据生成时间 |

前 7 个是**必须字段**，后 3 个是便利字段，接入方可按需取用或忽略。

## 四、数据为什么"像真的"

不是 `Math.random()` 直接取值，而是跑了一个微型业务模型：

1. **商品身份稳定**：商品池按固定种子生成（240 个），服务重启后货号与标题不变，只有数值重新演进。
2. **时间推进**：每次请求推进 1~3 个仿真小时，按电商真实作息曲线（凌晨低、午间与晚间双高峰）消耗库存。
3. **日切滚动**：跨天后 30 日销量窗口滚动，趋势因子随机游走，价格按店铺习惯缓慢调价（`.9` 结尾）。
4. **补货事件**：库存低于阈值时有概率"供应商到货"，避免库存永久归零导致数据失去观察价值。
5. **场景覆盖**：库存水平按业务场景抽样（断货 8% / 紧缺 20% / 健康 52% / 积压 20%），
   保证主系统的预警、补货建议、积压提醒都有素材可演示。

商品标题按「品牌 + 商品词 + 卖点 + 规格」组合，卖点绑定到具体商品，
不会拼出「笔记本支架 主动降噪」这类一眼假的搭配。品牌名均为虚构。

## 五、与主系统联动

两个终端分别启动：

```bash
# 终端 1：数据生产方
cd mock-data-service && npm start        # → http://127.0.0.1:4100

# 终端 2：业务消费方
cd .. && npm start                        # → http://127.0.0.1:3000
```

然后在主系统左侧菜单进入 **「数据源接入」**：

1. 确认「数据源地址」为 `http://127.0.0.1:4100`，点 **测试连接** 查看返回样例；
2. 点 **立即同步**，把仿真商品写入主系统；
3. 打开 **定时同步** 开关，主系统会按设定间隔自动拉取；
4. 到「商品库存」「智能补货」页面，即可看到仿真商品参与补货计算。

> **注意**：启用定时同步后，主系统内置的订单模拟会自动停止。
> 库存只能有一个数据来源，两套来源同时改写会产生无法解释的跳变。

## 六、配置项

全部通过环境变量覆盖，便于同机跑多实例：

| 变量 | 默认 | 说明 |
|---|---|---|
| `MOCK_PORT` | 4100 | 服务端口 |
| `MOCK_HOST` | 127.0.0.1 | 监听地址（局域网访问用 `0.0.0.0`） |
| `MOCK_POOL_SIZE` | 240 | 商品池规模 |
| `MOCK_POOL_SEED` | 20261102 | 建池种子，固定则商品身份跨重启不变；设 0 则每次启动随机 |
| `MOCK_BATCH_MIN` / `MAX` | 5 / 15 | 未指定 count 时的条数区间 |
| `MOCK_HOURS_PER_TICK` | 1 | 每次请求推进的仿真小时数 |
| `MOCK_STREAM_INTERVAL` | 2000 | SSE 推送间隔（毫秒） |

示例：

```bash
MOCK_PORT=4101 MOCK_POOL_SIZE=500 npm start
```

## 七、常见问题

**Q：端口被占用？**
A：换端口启动 `MOCK_PORT=4101 npm start`，记得同步修改主系统「数据源接入」里的地址。

**Q：主系统提示"数据源不可达"？**
A：本服务没启动，或地址填错。先在浏览器打开 `http://127.0.0.1:4100/api/health` 确认能返回 JSON。

**Q：想要每次都返回全新商品？**
A：请求时加 `?mode=chaos`。注意别让主系统长期用这个模式，否则商品会无限增长。

**Q：数据能固定下来方便排查吗？**
A：加 `&seed=任意字符串`，同样参数的结果可复现（`chaos` 模式完全可复现）。

**Q：如何接入真实电商 API？**
A：保持字段契约不变，把主系统 `server/services/datasource.js` 里的 `fetchProducts`
换成真实接口的调用与字段映射即可，补货算法、预警、采购单、看板均无需改动。
